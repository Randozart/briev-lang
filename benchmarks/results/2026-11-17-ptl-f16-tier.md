# 2026-11-17 — PTL f16 tier: the "9x regression" was the harness, not the kernel

## 0a. LATER THE SAME NIGHT — the tiled tier had a second, independent 16x bug

`briev_dev_vulkan.c` read `OpExecutionMode LocalSize W H D` and kept only `W` as the
workgroups' invocation count. Right for 1-D local sizes, wrong by `Y*Z` for every
2-D one — and the tiled GEMM declares `LocalSize 16 16 1`. So that tier has been
launched with **16x the workgroups it can use** since it landed, and (no tile guard
in the kernel) stored 16x outside its output, with `robustBufferAccess` off.

Fixed (runtime parses `X*Y*Z`, kernel gains a tile-range guard, `prepare_run`'s
formulas mirror the emitter). Measured, 4096³, same node:

| tier | before | after |
|---|---|---|
| tiled (f32 fixture) | gx=65536, **799.6 ms** | gx=4096, **39.3 ms** |
| cooperative-matrix f16 | 26.2 ms | 26.1 ms (1-D local size, unaffected) |

So the tiled tier is **2.4x faster than the hand-written CL-C reference**
(94.3 ms), not 8.5x slower. Both tiers now beat the reference at 4096³, and
`brievc run` agrees with the shipped artifact to 0.1% (26.373 vs 26.120 ms;
39.417 vs 39.411 ms) so quick iteration is trustworthy again.

## 0. OUTCOME (read this first)

`benchmarks/intel_ptl/ceiling/briev_lane.sh` measures with **`brievc run`**, which
does not execute the runner the compiler emits: it links a generic driver that
dispatches a different work-item count. For the coopmat tier that driver launches
**16x too many** workgroups; for other lanes it is wrong in the other direction.
Every Briev-lane ceiling number taken this way — including the 2026-11-09 record
that X1 was built on — is an artefact.

Measured the way a program actually ships (build → link the emitted `_runner.c` →
run), 4096³ f16, median of 3, same node, same binary:

| arm | ms | TFLOP/s |
|---|---|---|
| **coopmat, f16 accumulate (shipped)** | **26.23** | **5.24** |
| coopmat, f32 accumulate | 38.36 | 3.58 |
| no coopmat, f16 accumulate | 459.42 | 0.30 |
| no coopmat, f32 accumulate | 458.68 | 0.30 |
| f32 fixture (`Float` storage) | 801.91 | 0.17 |

512³ on the same path: **0.340 ms** (0.79 TFLOP/s) against the CL-C reference's
0.233 ms — 1.46x behind, which is the expected launch-bound shape, and a very
different story from the `run`-measured 1.05-1.62 ms.

Dispatch, built path: coopmat `gx=2048 local=64` (2048 workgroups — exactly the
tile grid the kernel decodes); naive f16 `gx=65536 local=256`; f32 `gx=65536
local=16`.

`benchmarks/intel_ptl/ceiling/briev_lane.sh` now builds, links and times that

So, corrected:

* **coopmat is not 9x slower than the f32 path — it is ~30x faster** than the f32
  fixture and **3.2x faster than the hand-written CL-C reference**;
* the shipped default (`coopmat: 1`, `f16acc: 1`) is the right selection, by a
  margin, and f16 accumulation beats f32 accumulation by 1.46x;
* X1's premise — "selection currently a regression shipped as a feature" — is
  **withdrawn**. There is no microkernel to fix and no fact-gate to add.

## 0.1 Why `brievc run` is not a measurement

`brievc run` writes only the `.spv`; `brievc build` additionally writes
`<name>_runner.c`, which the caller links. The two paths dispatch differently,
provably:

| fixture | `run` dispatch | built dispatch |
|---|---|---|
| coopmat f16 | `gx=32768 (nx=2097152)` | `gx=2048 (nx=131072)` |
| naive f16 | `gx=65536 (nx=16777216)` | `gx=65536 (nx=16777216)` |
| f32 | — | `gx=65536 (nx=1048576)` |

The coopmat tier is launched with 16x the tile grid under `run`, which is why it
"lost" by 9x: 367.8 ms is the same kernel doing 16x the work. 367.8/16 = 23 ms,
and the measured built-path figure is 26.2 ms.

**Action for the lane:** `briev_lane.sh` must build + link + run, or `brievc run`
must be fixed to dispatch the emitted geometry. Until then, any `.abv` number taken
with `run` — f16, f32, cooperative or not — is not a performance measurement. The
2026-11-09 ceilings table's Briev rows need re-taking; its CL-C rows come from
`ceiling_harness.c`, which is independent and unaffected.

### Verdicts

1. **The f32-accumulate hypothesis is refuted.** It was the headline candidate in
   the night queue ("the CL-C reference accumulates in f32"). It is not the lever:
   f32 accumulation makes the coopmat kernel **50 % slower** at 4096³
   (550.5 vs 367.8 ms), and the two non-coopmat arms are identical either way, as
   expected (that tier has no cooperative accumulator). Killed for the cost of one
   run — before any kernel work.
2. **The recorded A/B reproduces.** coopmat 367.8 vs tiled 460.5 at 4096³ against

3. **The 9× gap to f32 is real and is not about the accumulator.** 367.8 vs

4. **512³ is launch-dominated and unstable in this build** (1.29–1.62 ms across arms

## 4. An open discrepancy: the launched grid does not match the emitted runner

`BRIEV_ACCEL_VERBOSE=1` prints the grid, and the two tiers disagree with the
kernels' own tile decoding:

| arm | dispatch (observed) | local | cooperative-matrix ops |
|---|---|---|---|
| a (coopmat) | `gx=32768 gy=1 (nx=2097152)` | 64 | 45 |
| c (no coopmat) | `gx=65536 gy=1 (nx=16777216)` | 256 | 0 |

The non-coopmat arm is exactly one invocation per output (`nx = M·N`), correct.
For the coopmat arm the kernel decodes its tile from `wgid_x` with
`tiles_x = n/(64·subgroups)` (`src/backend/spirv/gemm.rs:3172`), i.e. **2048
workgroups** at 4096³ — yet 32768 are launched.

**But the emitted runner says otherwise, and that is the open question.** The same
build writes `_runner.c` containing

```c
long long n_gemm = 4096 * 4096;                    // 16777216
long long w_gemm = (n_gemm / (16 * 4 * 64)) * 32;  // 131072  == 2048 WGs at local 64
briev_accel_launch_resident(0, state, w_gemm);
```

which is exactly the tile grid. And the runtime cannot be inventing the factor:
`briev_accel_launch_resident` → `launch_resident_2d` → `launch_dev2d` forward `nx`
verbatim (`src/accel_rt.rs:847-905`), and the Vulkan side only divides by the local
size (`briev_dev_vulkan.c:1469`). A fresh `--out` directory reproduces `nx=2097152`,
so it is not a stale artefact.

So one of three things is true, and **none of them is established**:

1. `brievc run` executes a different runner than `build --llvm` emits (a
   build/run divergence) — the most likely, and the cheapest to test;
2. the coopmat kernel's real decode covers 16× more output than my derivation
   assumes, in which case the grid is right and my tile arithmetic is wrong;
3. `nx` is printed after some other transformation not found by reading the three
   functions above.

**A withdrawn claim.** An earlier draft of this file asserted the factor of 16 was
established and lived in `briev_accel_launch_resident`; reading that function
disproves it. The over-dispatch is a *suspicion with arithmetic behind it*, not a
finding, and it must not drive a code change until the divergence is explained.
The experiment that settles it: instrument the `run` path's generated runner (or
compare `briev_accel_launch`'s `work_n` argument between `run` and `build --llvm`),
then launch once on the derived tile grid and read the clock.

## 5. A measurement mistake worth recording

The first four-arm pass reported 367.899 / 367.887 / 367.849 / 367.779 ms — four
"arms" identical to 0.03 %. The cause: the loop set `BRIEV_HOME` and `CEIL_ROWS`
but **not** `CEIL_CONFIG_DIR`, so all four ran the shipped config. Identical times
across arms that should differ by ~25 % is the tell, and it is the same class of
error as the dead-pid soak and the shared `--out` corpus runner: an instrument that
reports a plausible number for the wrong subject. The corrected numbers above come
from runs that print their own config, and the per-arm dispatch lines confirm the
arms differ.

## 8. Why the reduce gap is not a bug (and must not be "fixed" by reassociating)

Investigating the last two red rows: the reduce kernel dispatches **16 workgroups**
(`gx=16, local=256`) with 0 barriers, i.e. one invocation per row, each looping K
serially. The CL-C reference instead uses one workgroup per row (4096 workgroups)
with a shared-memory tree reduce — more parallelism, and it is allowed to
reassociate the sum.

Our fixture says so in its own header:

```
// ceiling matrix: serial row sum ... General lane (no reassociation license):
// one serial K loop per work item.
```

So `reduce` measures the **unlicensed** lane, and being 2.2x behind a reference that
reassociates for free is the honest price of not doing that silently. The licensed
lane exists and is measured: `reduce_approx f16 = 0.106 ms` against the reference's
0.0969 ms — **1.09x**, i.e. essentially parity once the same freedom is granted.

That is the doctrine holding: a sum may only be re-associated when the program says
so, and the compiler prices the difference visibly instead of taking the win
quietly. Consequence for the lane: **there is no measured loss left to chase in the
ceiling matrix** — every shape where the language permits the reference's freedom
wins (elem, GEMM both dtypes and both sizes), and the one where it does not is 1.09x
of the reference through its licensed variant.

If reduce is ever worth real work, the honest route is a cooperative tree-reduce
**behind the existing licence** (`reduce_approx` should be the one to beat 0.0969,
and it is already at 0.106), not making the unlicensed lane faster by assuming
associativity it has not been granted.

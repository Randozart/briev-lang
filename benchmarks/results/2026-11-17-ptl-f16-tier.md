### Verdicts

1. **The f32-accumulate hypothesis is refuted.** It was the headline candidate in
   the night queue ("the CL-C reference accumulates in f32"). It is not the lever:
   f32 accumulation makes the coopmat kernel **50 % slower** at 4096³
   (550.5 vs 367.8 ms), and the two non-coopmat arms are identical either way, as
   expected (that tier has no cooperative accumulator). Killed for the cost of one
   run — before any kernel work.
2. **The recorded A/B reproduces.** coopmat 367.8 vs tiled 460.5 at 4096³ against
   the record's 371 vs 459. The 2026-11-09 numbers are sound, and with them the
   correction in the plan: coopmat *wins* the f16 A/B.
3. **The 9× gap to f32 is real and is not about the accumulator.** 367.8 vs
   39.56 ms on the same device, same night.
4. **512³ is launch-dominated and unstable in this build** (1.29–1.62 ms across arms
   tonight, 2.80–3.66 ms in a first, flawed pass; non-coopmat was fastest). Not a
   shape to draw conclusions from; 4096³ is stable to 0.1 %.

## 4. The new lead: the tensor tier over-dispatches 16×

`BRIEV_ACCEL_VERBOSE=1` prints the grid, and the two tiers disagree with the
kernels' own tile decoding:

| arm | dispatch | SPIR-V local size | cooperative-matrix ops |
|---|---|---|---|
| a (coopmat) | `gx=32768 gy=1 (nx=2097152, local=64)` | 64 | 45 |
| c (no coopmat) | `gx=65536 gy=1 (nx=16777216, local=256)` | 256 | 0 |

The non-coopmat arm dispatches exactly one invocation per output (`nx = M·N`,
256 per workgroup) — correct. The coopmat kernel decodes its tile from `wgid_x`
with `tiles_x = n/(64·subgroups)` (`src/backend/spirv/gemm.rs:3172`), i.e. 2048
workgroups at 4096³ — but it is launched with **32768**. `nx` is `M·N/8`, so the
host's elements-per-invocation (8) disagrees with the coopmat tile's
(64·128/64 = 128) by exactly **16×**.

If that factor is real, the same kernel does 16× the work: 367.8/16 ≈ **23 ms**,
which would beat the f32 path (39.6 ms) and the CL-C f16 reference (84.4 ms). That
is why this is the next experiment rather than a footnote.

**Traced to the generated runner, and the emitter is innocent.** An `.abv` build
emits `_runner.c`, and for this shape it contains:

```c
long long n_gemm = 4096 * 4096;                                   // 16777216
long long w_gemm = (n_gemm / (16 * 4 * 64)) * 32;                 // 131072
briev_accel_launch_resident(0, state, w_gemm);                    // nx = 131072
```

131072 invocations at 64 local = **2048 workgroups — exactly the tile grid.** The
emitter is correct; the runtime is handed the right number. `BRIEV_ACCEL_VERBOSE`
then reports `nx=2097152`, i.e. **16× the value passed**, with `16 = REG·REG`.

So the multiplication happens inside `briev_accel_launch_resident`, whose definition
is not in `lib/runtime/*.c` at all — it lives in the prebuilt
`target/compiler-in-briv/libbriev_accel_rt.a` (compiler-in-Briev), which is what the
generated runner links against. That archive is the next file to read, and the
`16` is almost certainly a "tiles → invocations" expansion that the coopmat grid
does not want.

Note for whoever picks this up: the archive is **host-built and not synced** by
`benchmarks/intel_ptl/run.sh` (it syncs `lib config plugins benchmarks` + `brievc`;
`run.sh` does carry `target/compiler-in-briv`, my manual sync did not), so a stale
archive is a live hazard for any A/B done this way.

## 5. A measurement mistake worth recording

The first four-arm pass reported 367.899 / 367.887 / 367.849 / 367.779 ms — four
"arms" identical to 0.03 %. The cause: the loop set `BRIEV_HOME` and `CEIL_ROWS`
but **not** `CEIL_CONFIG_DIR`, so all four ran the shipped config. Identical times
across arms that should differ by ~25 % is the tell, and it is the same class of
error as the dead-pid soak and the shared `--out` corpus runner: an instrument that
reports a plausible number for the wrong subject. The corrected numbers above come
from runs that print their own config, and the per-arm dispatch lines confirm the
arms differ.

## 6. K3 on this node: the limit does not bite here either

```
systemd-run --user --scope -p MemoryMax=256M  python3 -c "bytearray(512MiB)"
→ canary allocated 512MB in a 256M scope        (verdict: NOT enforced)
```

So the host-delegation gap is not specific to the workstation — **neither machine
can enforce `MemoryMax` for an unprivileged user**. `harness/edge_budget.sh`
already refuses to score in that case, on both. K3's blocker is therefore a
runner requirement (root, or `Delegate=yes` + `memory` in `cgroup.subtree_control`),
not "a better host", and the owner's four numbers remain the other half.

## 7. What is next, in order

1. **Trace `nx = M·N/8`** to its producer and test the 16× hypothesis by launching

2. Only if that fails: **X2 NEO residency** (OpenCL enumerates the same B390; the L0
   `launch_dev` shape is the template).
3. Re-run `ceiling/run.sh` (the CL-C reference) tonight before quoting 84.4 ms — it

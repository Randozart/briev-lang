# P0 — f16 KV Swap: correctness clean, bandwidth hypothesis refuted

**Date:** 2026-09-18

**Harness:** `F16KV=1 bash benchmarks/m3_attention_harness.sh <NKV>` +

**Device:** RTX 3060 (sm_86), driver 615.71.09, CUDA + Vulkan lanes

## Correctness: 36/36 PASS, exact

{bitnet 20/5, mellum 32/4, qwen 24/4} × NKV {256, 1024, 4096} × both
lanes, k/v as `Float16` (f32 q/s/o1/a_out): every run passes the 1e-3
gate with printed error 0 — the composition computes f32 on f16-loaded
values and the CPU reference decodes the same f16 storage, so the gate
measures pure composition error. `Float16` needed only
`import "std/types/float.bv"` in the instance.

## Performance: f16 does NOT move the composition (hypothesis refuted)

bitnet decode NKV=4096, CUDA lane, p50:

| Stage | f32 | f16 |
|---|---|---|
| push | 59.3 µs | 58.1 µs |
| qk | 227.1 µs | 229.4 µs |
| softmax | 40.1 µs | 38.0 µs |
| pv | 145.8 µs | 139.0 µs |
| chain | 413.0 µs | 406.4 µs (−1.6%) |
| stock ggml | 58–61 µs | — |

Halving KV storage bytes changed qk by +1%. The P2 model assumed KV byte
width was the dominant cost — **refuted**. qk moves ~10.5 MB in 227 µs ≈
46 GB/s effective (~13% of peak): the kernels are
latency/coalescing-bound. The qk work item (h, j) makes each thread
serially dot a full 512 B row while consecutive threads read rows 512 B
apart — scattered vec4 loads. ggml's VEC decode maps lanes over D
(coalesced 128 B segments) and reads ~4× more efficiently per byte.

## Consequence for the fused node (P2)

The fused node's win mechanism is **lane-over-D coalescing + one pass +
no launch chain**, not f16 byte-width (f16 still helps: same bytes, half
the sectors, and it is ggml's storage contract). The P2 gate stands:
fused+f16 must beat ~406 µs and approach ~58 µs, and the coalescing
analysis predicts the lane-over-D shape is what gets there. Honest risk
carried forward: if the in-loop lane-reduction latency (per-j subgroup
ops) eats the coalescing win, the gate fails and the negative is
recorded.

## Compiler fixes landed on the way (all additive)

`k[..] as Float` (compute-width widening) exposed three walkers that
dropped `Expr::Cast` — each fix is one recursive arm, no name matching:

- `collect_vec4_indices` — Cast around a load still collects as
  vec4-eligible (src/backend/spirv/lower.rs)
- `replace_index_in_expr` — Cast-wrapped `field[idx]` still rewrites to
  the synthetic vec4 component var
- `subst_var` / `subst_var_expr` — the vec4 fma group's scalar-side loop
  substitution now substitutes through the cast; before, the unrolled
  scalar reads kept the raw loop var and read garbage strides (Vulkan
  s_err=158 at NKV=256, caught by the f32-with-casts M3 probe — the f32
  regression that led to the f16 ones)
- PTX general emitter: widening-cast arm resolves the target through the
  casting graph (rule 19) — f32 targets lower to their operand; the
  elementwise surface already f16-loads natively (ld.global.u16 +
  cvt.f32.f16)

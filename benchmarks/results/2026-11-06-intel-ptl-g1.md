## What was built

`lib/runtime/briev_dev_levelzero.c` — the fourth `BrievDeviceDriver`, wired
into the chain per D2 (**Vulkan → Level Zero → OpenCL → CPU**;
`BRIEV_ACCEL_DEVICE=levelzero` override works):

- `available()`: dlopen `libze_loader.so.1`, `zeInit(GPU_ONLY)`, enumerate
  drivers/devices, pick the first `ZE_DEVICE_TYPE_GPU` (verified on PTL:
  `levelzero:8086:b082`), probe the compute queue-group ordinal.
- `init()`: context + **immediate command list** (D5; asynchronous mode; no
  counter-based events — Xe3, harvest §7.3).
- `create_kernel()`: `zeModuleCreate(ZE_MODULE_FORMAT_IL_SPIRV)` +
  `zeKernelCreate("main")` + OpExecutionMode LocalSize parse (same walk as
  the OpenCL driver), build-log capture on failure, kernel-name enumeration
  diagnostic.
- `launch()`: grow-on-first-launch **host-USM staging**
  (`zeMemAllocHost`, G1 simplification — device-accessible on iGPU), args
  `(ptr %state, i64 %n)`, group-size + flat grid, dispatch, host-sync,
  readback.
- Verified ABI values were read from the node's L0 1.32 headers (listed in
  the driver header comment).

## G1 verdict: driver skeleton works; the IL lane is BLOCKED on module flavor

Measured (full verbose log, 2026-11-06):

```
[briev_accel/levelzero] levelzero:8086:b082 ready (queue ordinal 0)
[briev_accel/levelzero] module exposes no kernels
[briev_accel/levelzero] zeKernelCreate("main") failed res=2013265937 (0x78000011)
[briev_accel] kernel 'selfadd' rejected by driver 'levelzero' — CPU fallback
```

- `zeModuleCreate(ZE_MODULE_FORMAT_IL_SPIRV)` **succeeds** on Briev's blob —
  consistent with the harvest probe (§3.1a).
- The compiled module exposes **ZERO kernels** (`zeModuleGetKernelNames` →
  count 0), so `zeKernelCreate("main")` fails
  (`0x78000011`, kernel-name invalid).
- The OpenCL/IL lane showed the same disease from the same IGC
  (`CL_INVALID_KERNEL_NAME`, empty name list — BUGS.md 2026-11-06).
- Control experiment (harvest §3.1a): a standalone **OpenCL-flavored**
  SPIR-V module (clang `-x cl`, kernel `k`) created its kernel fine on this
  driver. Briev's `.bv` kernels are **Vulkan-flavored** (`OpCapability
  Shader`, `OpEntryPoint GLCompute`, storage-buffer semantics).

**Conclusion:** IGC's IL path accepts Vulkan-flavored modules silently but
compiles them to an empty kernel set. The unblocking work is a bounded,
derivable **OpenCL-flavored SPIR-V projection** of the same kernel image
(`OpCapability Kernel` / `OpEntryPoint Kernel`, OpenCL memory model, SSBO →
kernel argument) — the "vendor projection from ONE frontend plan" the design
doc predicted. Until then, **Vulkan is the only working Intel lane** (G0
PASS), and the chain's ordering (Vulkan → L0 → OpenCL) is validated in the
fall-through direction: a driver that rejects a kernel hands off to the next
one cleanly, exactly as `abv-gpu-doctrine.md` §3 requires.

No performance numbers are recorded at this rung (no kernel executed).

## Process hazards hit (recorded per BUGS.md playbook)

1. The working-tree hazard (BUGS.md 2026-08-27) recurred in this worktree:
   `briev_dev_levelzero.c` transiently vanished mid-session (tar "Cannot
   stat" at one moment, present the next), and a rebuild picked up a
   stale/pre-fix `briev_dev_vulkan.o` (pipeline failures reappeared with no
   source diff). Mitigations that worked: `md5sum` on every sync, `strings`
   checks on archives/binaries for the expected markers, clean rebuild
   (`rm *.o *.a && touch build.rs`) after confirming source stability, and
   never trusting a sync without a verification print.
2. `brievc run` links the accel runtime from
   `$BRIEV_HOME/target/compiler-in-briv/` **at program build time** — a stale
   archive there silently downgrades every lane (this is how the pre-fix
   vulkan.o masqueraded as a regression).

## Correctness (the kernel-index gate — verify output, not just timing)

| Lane | Shape | Gate | Result |
|------|-------|------|--------|
| SPIR-V / Vulkan | 4096³ | all-ones seed → y[m][n] must == K=4096 EXACTLY | **PASS** 4096/4096 cells, maxrel=0 |
| SPIR-V / Vulkan | 4096³ | naive f64 ref | ~4.5% per-cell (maxrel 0.045 ≤ 6% tol = **PASS**) — the kernel's declared `acc: Float16` accumulator (gemm_h.abv), NOT an addressing bug |
| SPIR-V / Vulkan | 4096³ | coverage probes: 4 matrix corners + center | **OK** — full matrix computed, uniform f16-acc bias |
| CUDA / cubin | 4096³ | any | **IMA** (illegal memory access rc 700) — see BUGS.md 2026-09-30 |
| both | 64³ (gemm_small) | counter fast-forward | PASS (i=4096) |

Two reference traps recorded so they are not re-litigated:
1. A sequential-f16 reference is the WRONG oracle at K=4096 — device
   (parallel coopmat f16-acc) and sequential-f16 orders legitimately
   diverge up to ~10% (f16 spacing ≥ 16 at that magnitude). Use the
   f64-exact reference with the ≤6% tolerance.
2. The bench helpers' `f32_to_f16` had a wrong carry check
   (`m == 0x800u`, must be `m == 0x400u`) that fired on exact-halfway
   inputs (8191.5 → 4096 instead of 8192), corrupting the reference.
   Fixed in `benchmarks/gpu/gemm_h_bench.c` and
   `benchmarks/gpu/mma_ceiling_bench.c` this session; present since
   `c122ead2`/`38f07e2c`.

The all-ones gate is the addressing oracle: seed a=b=1.0 (f16-exact), so
every output must be exactly K. Any wrong row/col/index/OOB read would make
some cell ≠ K. It passes 4096/4096 at 4096³, so the SPIR-V kernel's
addressing is correct at the full shape. A naive f64 reference is the WRONG
oracle here (the kernel accumulates in `Float16`, ~4.5% error for K=4096);
do not "fix" the kernel to match a f64 reference.

### Root cause: NVIDIA driver 615.71.09 (installed 2026-09-17)

pacman log: `580.178.04-1` → `615.71.09-2` on 2026-09-17 14:53. All
4.55-era records predate the upgrade (plans record driver 580.178);
results from 09-18 on record driver 615. Isolation probes, all on
615.71.09, same machine:

| Probe | Shape of work | 580-era record | on 615 today | Verdict |
|-------|---------------|----------------|--------------|---------|
| `mma_ceiling_bench` f16acc | register-resident coopmat + L2 loads, no smem/barriers | 50.1 ms/launch | **50.3 ms/launch** | unchanged |
| `gemv_bench` coop 4096 | workgroup/subgroup reductions | 0.199 ms (09-02) | **0.193 ms** gpu_time | unchanged |
| `gemm_h` tensor 4096³ | DRAM→smem fill, workgroup barriers, coopmat from smem | 4.55 ms (09-07) | **11.46 ms** (era kernel) | **2.5× slower** |

Hardware and compiler both healthy: ceiling and GEMV sit at their
580-era numbers, and the era-commit kernel reproduces the same ~11.5 ms
as the tip. The regression is isolated to the workgroup-smem + barrier
pipeline inside the vendor driver. Tracking: BUGS.md "NVIDIA 615.71.09
regressed the smem-fill/barrier compute path". Portable-lane GEMM
numbers below that table's 4.55-era figures are **driver-bound** until
the vendor issue is resolved; the PTX/CUDA tier (`ptx_gemm_bench`,
23.4 TF referenced pre-615) is the other lane — its 4096³ IMA remains
open (see below).

Sanity anchors on 615: naive f32 @4096³ = 1.9 TF (2026-09-20 baseline);
cuBLAS anchor @4096³ = 42 TF.

## Lane selection (this session's change)

`select_driver` is now image-aware: a PTX-bearing desc → CUDA preferred;
a SPIR-V-only desc → Vulkan preferred. The 4096³ runner carries BOTH a
SPIR-V and a cubin, so it auto-selects CUDA and hits the cubin IMA — which
is why the SPIR-V/Vulkan lane is the verified-correct 4096³ lane until the
cubin IMA is fixed. Force Vulkan with `BRIEV_ACCEL_DEVICE=vulkan`.

## Related fix (this session)

`briev_accel_download` now skips `is_write == 0` (host-authoritative

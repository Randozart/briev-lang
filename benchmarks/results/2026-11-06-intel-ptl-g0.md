## Defects found and fixed by this rung

1. **Vulkan stage bit** `VK_SHADER_STAGE_COMPUTE` was `6` (invalid) — every
   strict-driver pipeline failed; fixed to `0x20`.
2. **`.bv` accel descriptors** emitted an empty field table because prelude
   `StateDecl`s are not in the program field map; the old code aborted on the
   first foreign name. Fixed with a skip + regression test
   (`test_accel_descriptors_skip_foreign_state_fields`).
3. **OpenCL `available()`** counted GPU devices but never fetched a handle
   when the platform had a GPU; fixed (context creation now succeeds).
4. **OpenCL/IL on NEO** entry-point lookup — OPEN (lane unusable today).
5. **Large `%State` frame** (8 MB+ state) exceeds the default stack — OPEN;
   G0 runs with `ulimit -s 65536`.
6. **`let f: Float = 0`** emits `store float 0` (invalid IR) — OPEN; use
   `0.0`.

Full details and repros: `BUGS.md` (2026-11-06 entries).

## Interpretation

- Briev's portable SPIR-V lane executes correctly on Xe3 through Vulkan;
  the existing emitter/descriptor/runtime architecture needs no Intel-specific
  kernel fork for this rung.
- The two defects in (1) and (2) were **validation strictness** gaps that
  NVIDIA tolerated; both would have blocked any Intel lane. They are
  architecture-neutral fixes.
- No performance comparison with OpenVINO is made here: geometry and lane
  differ, and G0's tiny `gpu_time` is dispatch-only. The first fair
  comparison is G5 with the collector.
- Next rung: **G1** — Level Zero driver skeleton (`available/init/
  create_kernel`, sentinel dispatch), then G2 projection launches and G3
  coopmat negotiation.

## Addendum — §12 W3 sum idiom gate (2026-11-06)

`g0.sh` now also runs `g0_sum` (hand-written `acc = acc + a[i*K + k]`,
ROWS=4096, K=1024 Int — the §12 idiom lane) on Vulkan:

```
-- g0_sum on vulkan: bad=0 gpu_sum=0 cpu_sum=0 # gpu_time: 0.002 ms
   PASS
```

- The detector (`detect_sum_fold`) fires; the lane license
  (`sum_reduce_lane`: Int + const K % 32) holds; the SPIR-V lowers to
  `GroupNonUniformIAdd` with LocalSize 32 (one 32-lane subgroup per row,
  flat-1D `row = gid>>5`); the dispatch wrapper sends rows×32 invocations
  while the counter still stores rows.
- `BAD=0` is the gate: verify recomputes every sampled row exactly and
  compares to the device output (Int — no tolerance). The sampled sums are
  **legitimately 0** (the 7-cycle row-sum offsets cancel over the 256
  samples) — the equality count, not the sum, is the correctness signal.
- CPU-fallback lane checked too (`--accel-cpu-fallback`): `BAD=0`.
- Disclosure: `info: reduce-idiom (assoc add, int) → reduction synthesis
  (warp-slice) for accel 'rowsum'`.

### Findings recorded during the gate

1. **Report-precondition trap (authoring):** the gate's original report
   pre used `gpu_sum >= 0` as a liveness anchor; sampled sums are signed,
   so the pre became false forever and the reactor ran until killed.
   Anchor with a value-unconditional bound (`>= -1e12`) instead. A
   self-equality tautology (`x == x`) is folded away and does NOT keep the
   field live — the accumulator stores are then eliminated.
2. **Dead-field diagnostic misses `endprogram println!` reads:** a field
   printed by the swan song is reported "never read — wasted work"
   (value still prints correctly; the diagnostic is wrong). BUGS.md
   2026-11-06.
3. **G001 cross-thread-stride warning** is computed on the pre-synthesis
   body (`a[i*K+k]`, stride K) while the chosen sum lane reads coalesced
   `a[row*K + lane + t*32]`; the disclosure is inaccurate for synthesized
   lanes (W4 item).

### W3.1 min/max gate re-enabled — PASS (2026-11-08)

`g0_minmax` is a required Vulkan rung again after the P0 fix
(`docs/plans/2026-11-08-general-workstream-countable-body-and-folds.md`):

```
-- g0_minmax on vulkan: bad=0 MIN=ok MAX=ok # gpu_time: 0.003 ms
   PASS
```

The earlier failure was NOT the idiom lane: `emit_countable_body`
(`loop_engine/counter.rs`) silently dropped nested `foreach` loops via its
`_ => {}` fallthrough, so the folded max node emitted `ymax[j] = a[j*K]`
instead of the row max. Fixed by delegating every executable statement form
to `emit_stmt::emit_statement` and making the match exhaustive (no wildcard);
regression pinned by `tests/countable_body_foreach.rs`.

### P1 float-fold gates — PASS (2026-11-08)

The numeric ambiguity pair `approx` / `exact` (node/txn prefix) is the author
surface; default stays precise.

```
-- g0_fsum_approx on vulkan: bad=0 SUM=ok # gpu_time: 0.009 ms   PASS
-- g0_fsum_exact  on vulkan: bad=0 SUM=ok # gpu_time: 0.006 ms   PASS
```

- `g0_fsum_approx`: float row-sum under `approx` — the reassociated warp-slice
  lane (`GroupNonUniformFAdd`) runs; the data is integer-valued in f32, so the
  reassociated result is bit-exact and the gate stays strict (`BAD=0`).
- `g0_fsum_exact`: the same fold under `exact` — the lane is suppressed and the
  general per-work-item sequential lowering runs; `BAD=0` vs the sequential
  host reference.
- Disclosed at build: `fold-idiom (reassoc add, float, approx-declared ...)`.

**`-ffast-math` A/B (2026-11-08):** same `.ll`, linked with and without the
flag, on a rounding-sensitive sum: both `16777216` — the link flag does not
relax emitted IR that lacks instruction fast-math flags. Precise default holds;
`exact` is enforceable. (The flag stays as a codegen-policy detail; rerun the
A/B when the toolchain changes.)

**Latent `!>` bug found:** `!> associative` / `!> fp_math: fast` would emit
`reassoc` / `fast` as bare FUNCTION attributes, which clang rejects (they are
instruction flags). The keyword path deliberately emits none — BUGS.md
2026-11-08.

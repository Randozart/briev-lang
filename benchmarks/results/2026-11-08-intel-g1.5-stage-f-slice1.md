# Intel G1.5 Stage F — slice 1 (OpenCL projection) implementation record

**2026-11-08.** First vertical slice of the Stage F projection, per the design
constraints in `2026-11-08-intel-g1.5-stage-f-design.md`.

## What landed

- `SpirvFlavor { Vulkan, OpenCL }` on `SpirvBuilder`:
  - OpenCL: `Kernel` + `Addresses` + `Int8` capabilities,
    `OpMemoryModel Physical64 OpenCL`, entry model `Kernel`, entry name
    `briev_kernel` (the flavor owns model and name in `set_entry_point`).
  - Vulkan: unchanged (`Shader`, `Logical/GLSL450`, `GLCompute`, caller name).
- OpenCL state ABI: the state is kernel argument 0 (`ptr CrossWorkgroup u8`)
  plus the dispatch bound `n` (u64), created as `OpFunctionParameter`s of the
  entry function. Field access lowers through byte-offset
  `OpInBoundsPtrAccessChain` + pointer bitcast using the SAME `projection_offsets`
  layout as Vulkan (no Block/Offset decorations — they require Shader).
  Vec4 FMA groups use 16-byte group offsets on the same base.
- Scope boundaries (capability errors, Vulkan fall-through): GEMM
  (tensor/tiled/coopmat), image bindings, and f16 state stay Vulkan-only for
  this slice.
- Dual image through the descriptor:
  - `BrievKernelDesc` appends `opencl_spirv` / `opencl_size` (offset 96/104,
    sizeof 112; C header + Rust mirror + LLVM struct + ABI pins updated).
  - `.abv` runner C emission carries `ko<N>` arrays + descriptor args.
  - `.bv` LLVM path embeds `@briev_kernel_<txn>_ocl` when the image exists.
  - `accel_rt::kernel_blob` prefers the OpenCL image for the `levelzero` and
    `opencl` drivers; absent → Vulkan blob fall-through.

## On-device verification (PTL, 2026-11-08/09)

Fast per-lane check: `benchmarks/intel_ptl/g1_lane_smoke.abv` (one 256-lane
workgroup, `dst[i] = 2i+1`; the runtime prints the endpoints).

```
levelzero: kernel 'scale' compiled on 'levelzero'
           dst[0] = i64 1 | dst[255] = i64 511
opencl:    kernel 'scale' compiled on 'opencl'
           dst[0] = i64 1 | dst[255] = i64 511
```

Both lanes accept the OpenCL-flavored module (entry `briev_kernel`), launch
it, and read back correct results. Fixes found on the way (latent — the lane
had never launched a kernel before):

- L0/OpenCL drivers assumed the entry was named `main`; they now ask the
  module/program for its kernel names (prefer `briev_kernel`).
- OpenCL builtins must be IMPORTED (`LinkageAttributes "__spirv_BuiltIn…"`,
  `Constant`) with `vec3<u64>` components under Physical64; a plain Input
  variable reads gid 0 on NEO (every lane wrote element 0).
- `zeMemAllocHost` was called with the DRIVER handle instead of the CONTEXT
  handle (immediate segfault on first real launch).
- OpenCL buffer flags were `0x3` (WRITE_ONLY|READ_WRITE → CL_INVALID_VALUE);
  now `CL_MEM_READ_WRITE` (1). Added `mapped` for the runtime's field
  download; drivers without residency ops report `download` as a no-op
  (the full-copy `launch` already unpacks outputs).
- `g0.sh` lane report now runs the fast smoke fixture; a wrong endpoint is a
  gate failure, not a report.

## Blocker for full-g0 lane promotion

`g0_elem.bv` (const N = 1048576) emits an enormous CPU-lane IR (641 MB,
13.6M lines: the const-bound init/verify loops are unrolled), and linking it
on the node exceeds 45 minutes. "All six fixtures on Level Zero" is therefore
gated by that pre-existing compile-time blowup, not by Stage F. Promotion of
`levelzero`/`opencl` to REQUIRED waits for either (a) a long-running gate
session, or (b) the unroll/const-bound compile-cost fix. The fast lane smoke
covers compile+launch+readback in the meantime.

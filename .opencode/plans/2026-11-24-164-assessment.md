# Is #164 the right thing to merge, and what would it take? (research, 2026-11-24)

**Question.** PR #164 (`fix/wasm32-read-narrowing`) moves `cross_target_ir.sh
wasm32-unknown-wasi` from 52 failures to **15** — the best result of the whole
stack — but regresses `tests/rbv_list_each_wasm`. Is the approach right, and
what is the real cost of landing it?

**Answer in one line.** The *diagnosis* is right and the *number is real*; the
*mechanism* is a name-keyed side table consulted at some conversion sites and
absent at others, and it reintroduces a failure mode this repo already
documented as bug #119. Landing it safely is either a ~1-day hardening or a
~1-week structural change that removes the whole class.

---

## 1. What #164 actually does

Three mechanisms, all in `src/backend/llvm/`:

- **A width record.** `FunctionContext::reg_value_ll: HashMap<String, String>`
  maps a register **name** (`"%t11"`) to the LLVM type it was physically emitted
  as (`"i32"`, `"i64"`, `"ptr"`). Written at loads
  (`helpers.rs:3409`, `self.fun.reg_value_ll.insert(val, llvm_ty)`), at an
  `inttoptr` result (`helpers.rs:3635`), and at one arena site
  (`emit_toplevel.rs:8331`).
- **Consultation.** `value_width_or_target_width` (`emit_expr.rs:7251`) returns
  the record, falling back to `i{int_bits}`. `narrow_handle_to_target_width`
  (`emit_expr.rs:7265`) truncates a wider record down to the target word before
  an `inttoptr`, because `inttoptr` declares its source width and LLVM requires
  an exact match.
- **A pointer/handle round-trip.** `pointer_handle_of` (ptr → i64 → target word)
  and `pointer_from_handle` (word → ptr) bracket every "store a pointer-ish
  value" site: `emit_expr.rs:4898-4904`, `emit_stmt.rs:3901`, `emit_stmt.rs:4059`.

The diagnosis is exactly the architecture's own rule
(`docs/architecture/backend-type-dispatch.md:50`):

> **A type is one machine word unless a bit width is explicitly given as
> metadata.** … flexible types (`Int`, `UInt`, `String`) are exactly one machine
> word: `int_bits` wide … derived at codegen time.

On wasm32 that means `i32`; the backend is full of hardcoded `i64`. Measured on
this tree: **119 `call i64`, 111 `store i64`, 90 `inttoptr i64`** = 320 sites.
That is the true size of the class, and it explains both why two slices moved
52 → 15 and why the remainder is not a small tail.

## 2. Does it work? Yes, measurably

| gate | before #164 | after #164 |
|---|---|---|
| `cross_target_ir.sh wasm32-unknown-wasi` | 52 / 100 | **15 / 100** |
| `cross_target_ir.sh aarch64-unknown-linux-gnu` | 0 / 100 | 0 / 100 |
| native IR, 12-fixture byte compare | — | **identical** |

So the value is real and the native path is untouched. This is the PR that
actually moves the campaign.

## 3. Why it regresses — and why that shape is familiar

`rbv_list_each_wasm` fails after the merge and passes at #163 (A/B confirmed by
resetting to the #163 merge and re-running). Reproducer:

```bash
./target/release/brievc build tests/fixtures/generic_wasm_scan.rbv --split \
    --out /tmp/wscan --stdlib-path lib --config-dir config
```

```llvm
%t8  = bitcast <{ i64, [6 x i8] }>* @str.24 to ptr
  %t10 = ptrtoint ptr %t8 to i64        ; pointer_handle_of: adapt_to_i64
  %t11 = trunc i64 %t10 to i32          ; pointer_handle_of: narrow to target word
  store ptr %t11, ptr %t9               ; ...then stored AS a ptr
```

The narrowing is correct. The store is not: a *word* reached a `ptr` operand.

The mechanism is `pointer_from_handle` (`helpers.rs:3628-3629`):

```rust
let hw = match self.fun.reg_value_ll.get(handle) {
    Some(w) if w == "ptr" => return handle.to_string(),   // ← assumes it is already a pointer
    _ => self.value_width_or_target_width(handle),
};
```

A `"ptr"` record means "no conversion needed". But the record is keyed by
register *name*, and names are reused — which is precisely the bug this repo
already paid for:

> **context.rs:1553-1563 (issue #119).** `iter_chain_loop` starts again at `%t0`
> while the map still held `%t61 = ptr` from the previous body — so `canonical_ptr`
> passed an i64 handle through un-converted and the element GEP emitted
> `getelementptr i64, ptr %t61`, invalid IR.

Same class, different helper. #164 cleared the map on `reset_register_names` and
`clear_locals` (both documented, with a test at `tests.rs:15415-15437`), but
`restore_preserve_counters` (`context.rs:1902`) does `*fun = self.saved` while
keeping the counter monotonic — so records added *inside an inlined txn body* are
discarded, and the map's authority is inconsistent by construction: reliable at
some sites, silently absent at others. An "I don't know" that resolves to
"already a pointer" is the dangerous direction.

**Residual uncertainty, labelled.** From the emitted IR I can confirm the *class*
(a narrowed word reaching a `ptr` operand) and the *site family* (one of the
three `pointer_handle_of` → `pointer_from_handle` round-trips — the IR shows
`ptrtoint`+`trunc`, not the hardcoded `inttoptr i64`). What I have not isolated
is *which* path stamped `"ptr"` on that truncated register: the early return is
the only way `pointer_from_handle` yields a non-pointer, so either the record is
stale for that name or a writer I did not find set it. Answering that is step 0
of Option A, and it is a 10-minute instrumented build (`eprintln!` in the early
return with the register name), not open research.

## 4. Is the approach right?

**As diagnosis: yes.** **As mechanism: no — it is the fourth partial channel for
a fact that belongs on the value.**

Today a conversion site has to answer "what is this operand's LLVM type?" from:
`TypedRegister.ty` (the Briev type), `reg_value_ll` (physical width, sparse),
`reg_llvm_ty` / `reg_float_cache` (other side tables), and hardcoded `i64`
literals. `TypedRegister` (`mod.rs:617`) is `{ name: String, ty: Type }` — no
LLVM type, which is the hole every one of these mechanisms is trying to plug.

The wider world is unanimous, and LLVM says it explicitly:

- **LLVM**: `Value` holds `Type *VTy` (`Value.h:118`), read via `getType()`
  (`:257`); `IRBuilder`'s name argument is only a hint. The Programmer's Manual
  is blunt: *"names should ONLY be used for debugging … they should not be used
  to keep track of values or map between them."*
  ([Value.h](https://github.com/llvm/llvm-project/blob/main/llvm/include/llvm/IR/Value.h#L118),
  [PM](https://llvm.org/docs/ProgrammersManual.html#the-value-class))
- **Go**: `Value` carries `ID`/`Type`; *"The name of an SSA Value is not
  semantically significant, and may not even be unique within a function."*
  Side tables key on `ID`, never on a name.
  ([ssa.go:129](https://github.com/golang/tools/blob/master/go/ssa/ssa.go#L129))
- **Cranelift**: values are dense indices into
  `PrimaryMap<Value, ValueDataPacked>` with the type packed into
  `flags_and_type`, read by `dfg.value_type(v)`.
  ([dfg.rs:393](https://github.com/bytecodealliance/wasmtime/blob/main/cranelift/codegen/src/ir/dfg.rs#L393))
- **QBE**: the type is written at each definition (`%x =w add`), i.e. it is
  carried by the value in the text itself.
  ([il.txt](https://c9x.me/qbe/doc/il.txt))
- **The nearest exception is instructive**: LLVM's MIR keeps
  `VRegToType`, but keyed by a **dense vreg index**, not a name, with an explicit
  invalidation hook (`clearVirtRegTypes()`).
  ([MRI.h:807](https://github.com/llvm/llvm-project/blob/main/llvm/include/llvm/CodeGen/MachineRegisterInfo.h#L807))

Implication for a textual emitter keyed by `%tN`: the map must be either
**total and authoritative** (every register, including narrowing and conversion
results) or **absent** (derive from the Briev type through the casting graph).
Anything in between is a claim about width that is sometimes true.

## 5. What landing it would take

### Option A — harden it (~1 day, keeps the number)

1. **Delete the unsafe shortcut.** `pointer_from_handle` must not treat `"ptr"`
   as "skip conversion" when the argument came from a narrowing step. Either
   take the Briev type as an argument (a `Ptr<T>`/`String` value *is* a pointer;
   an `Int` handle is a word) or drop the early return and let callers that
   already hold a pointer skip the call themselves.
2. **Make the record total at the conversion sites.** `pointer_handle_of` must
   record its trunc result's width (`i{int_bits}`), so the inverse operation can
   never read a stale/absent record.
3. **Remove the round-trip.** `pointer_handle_of` → `pointer_from_handle` around
   a store is `ptr → i64 → i32 → ptr` for a value that was already a pointer.
   The three sites (`emit_expr.rs:4898`, `emit_stmt.rs:3901`, `:4059`) should
   store the pointer directly when the value's Briev type is pointer-like.
4. **Fix the two unpatched `store ptr` sites** that still hardcode
   `inttoptr i64` (`emit_expr.rs:7494-7500`, and the parallel arms at
   `emit_stmt.rs:3903`/`:4061`) — or delete them in favour of
   `emit_non_scalar_store`.
5. **Pin it as an invariant, not a fixture.** A check that walks emitted IR and
   rejects any `store ptr` / `getelementptr` / `inttoptr` whose operand's
   declared type is not `ptr` would have caught this and #119. That is a
   ~40-line verifier pass over the module; it belongs next to
   `src/ir_verify.rs`.

### Option B — remove the class (~1 week, deletes the mechanism)

Give `TypedRegister` its LLVM type:

```rust
pub struct TypedRegister { pub name: String, pub ty: Type, pub llvm_ty: String }
```

Every conversion then consumes `llvm_ty` — the value answers for itself, as in
LLVM/Cranelift/Go/QBE. `reg_value_ll` disappears, as do the
`adapt_to_i64`/`ensure_typed_value`/`narrow_handle_to_target_width` guesses and
the 320 hardcoded `i64` emissions (each becomes `llvm_ty`, which is `i64` on
hosts — so native IR stays byte-identical, which is exactly the invariant this
repo already uses to judge such refactors).

Cost: `TypedRegister` is constructed in ~hundreds of places; the honest estimate
is a week of mechanical work plus the gate cycle. Payoff: the wasm32 class stops
being a campaign and becomes a property of the emitter. It also retires the
#119 failure mode structurally rather than by `clear()` discipline.

### Option C — split (what I recommended on the PR)

The aarch64/arena handle work in the same branch is independent of the
read-narrowing experiment. Splitting lets the safe half land now and keeps the
shaky half out of `main` until (A) or (B).

## 6. Recommendation

**Do not merge #164 as-is.** Its regression is not a fixture quirk — it is the
name-keyed-map failure mode this repo documented as #119, and the early return
that causes it is one line that will keep firing in new shapes.

**Merge order I'd argue for:**

1. **Now:** split out the aarch64/arena half (Option C) — independent, verified.
2. **Next (~1 day):** Option A. Land the 52 → 15 win with the shortcut removed,
   the record made total at the narrowing sites, and the emitted-IR invariant
   checker added. That checker is worth more than the fix: it converts "invalid
   IR reached the linker" into "the emitter produced a mistyped operand", which
   is the diagnostic this codebase has been missing all along.
3. **Then:** Option B as a funded refactor, using the invariant checker as the
   gate and native-IR byte-identity as the safety net.

**Not recommended:** merging #164 unchanged and fixing forward on `main`. The
failure shape is silent on 64-bit hosts (it only manifests where the target word
differs from the hardcoded literal), so forward-fixing means shipping a known
latent regression into the one configuration CI's native matrix cannot see.

## 7. Open questions worth answering before Option A

- Does `restore_preserve_counters` discarding in-body records explain the
  remaining 15, or are those a different class? (Instrument
  `reg_value_ll` misses and count them per site.)
- Is the "second print emitter" from the #163 finding (BUGS.md 2026-11-24) the
  same mechanism — an emission site that builds `call i64 @sym` without going
  through `print_call_ret_ty`? If so, Option A covers it and the two findings
  collapse into one.
